# UI/UX 设计标准工作流

**这是明确确认过的工作方式，不是建议。开始画任何一屏之前先读完，然后按顺序执行。**

一句话：**完整度 → 代码对齐 → 美观 → 细节优化**。每一步做完都要如实核对、不自己瞎拍板、发现问题直接改并留痕。

---

## 第 0 步：加载项目配置

流程本身是通用的，但「去哪儿查代码、文案、配色，产出放哪」每个项目不同。这些值放在**项目根目录**的：

```
.claude/ui-ux-design-flow.config.md
```

- **文件存在** → 读它，把值代入下文所有 `{{变量}}`，直接进第一步。
- **文件不存在** → 做一次**尽量短**的安装问答，然后按 `config.example.md` 的结构写入上述路径，请用户确认，再进第一步。

问答规则，按顺序做，别一上来就甩 14 个问题：

1. **先自己查，能查到的不要问。** 项目名取文件夹名；技术栈看 `pubspec.yaml` / `package.json` / `*.xcodeproj` 判断；仓库地址读 `git remote -v`；设计稿目录看有没有现成的 `docs/design/` 之类。查到什么就直接填好，在确认时告诉用户"这几项我自己填了"。
2. **只问 A 组必答 4 项**（代码本地路径、页面代码目录、文案来源、配色/主题来源），**一次性列全**，不要一条一条来回。
3. **B 组选填 10 项一律先走默认值**，不要问。等真正用到某项、且默认值不适用时再单独问那一项。
4. **C 组踩坑清单初始留空。**

⚠️ **A 组 4 项里但凡缺一项，就停下来问，不要往下走。** 没有真实代码可对照时，第二步「代码对齐」只能照需求文档的文字瞎编——这正是本工作流要杜绝的头号问题。宁可卡住问用户，也不许凭想象画。

---

## 第一步：从需求文档推导完整页面清单

目标是**页面结构不缺**，不是先画得好看。

- 通读 `{{PRD_LOCATION}}` 里的需求文档，把这个聚类涉及的**所有页面/所有状态**全部列出来，做成 checklist。
- 必须包含（最容易漏的就是这些）：
  - **空态**（数据为空白的状态）
  - **重试 / 加载 / 异常态**
  - 重要页面的**操作成功页**、**操作失败页**
  - **未选中 / 默认未填 / 禁用**等样式
- 列完之后**主动核对一遍有没有漏页**，确认逻辑上不存在缺失的中间页（比如有确认页没有结果页、有列表没有空列表）。
- 这一步的产出是清单 + 页面跳转关系，先给用户过一遍再往下走。

## 第二步：结合代码补齐清单中的页面（含原有实现）

新增内容必须长在**真实的现有页面**上，不是凭空画一个新页面。

- 去代码仓库 `{{CODE_REPO}}`（本地 `{{CODE_LOCAL_PATH}}`）查每个涉及页面的**现有实现**：这个页面原本有哪些信息模块、什么顺序、什么组件。
  - 分支约定：`{{BRANCHES}}`。对比"线上现状 vs 下个版本"时，读线上分支看今天的样子，读开发分支看即将上线的。
- 把原页面的信息**一个都不漏地**先摆回去，再决定新增的模块插在哪、怎么排。
- 然后在"修正后的页面"基础上优化新增内容加入后的样式/排版/布局。

### 画每一屏之前，先从代码回答这四个问题

别把需求文档字面直译成像素 —— 文档可能是错的、过时的，或者描述的**根本不是 UI 改动**。

1. 这个页面/组件**已经存在**吗？它上面**实际**有什么？
2. 我要画的是**视觉**改动，还是只是行为/后端改动？若是后者，**一屏都不该画**，直接说明情况。
3. 这个元素是**常驻**的，还是**交互触发**才出现的？
4. 我描绘的这条流程，真的能走到这个状态吗？

优先**复用既有组件**，不要发明新的。

代码取值位置：页面在 `{{PAGE_DIR}}`；文案一律取 `{{COPY_SOURCE}}`；配色取 `{{THEME_SOURCE}}`。

⚠️ **不要按命名猜值，一律打开文件读实际内容。** 这不是洁癖，是真翻过车的：常量名可能是历史遗留（某项目 `AppColors.mint` 的实际色值是紫色 `#845EC9`，整套 `mint500/600/700` 全是紫色阶）；文案方法名也可能和内容对不上（某项目 `...PassportTitle` 取出来的字符串其实是 `Diary $name`）。本项目自己的坑记在配置文件第 5 节，每发现一条就补进去。

## 第三步：页面样式优化

完整度过关之后，才动配色、间距、视觉层次。

- 这一步要**有创意**、保证视觉美观性。
- 同时**不能因为好看而丢信息** —— 该页面应该展示的信息一个都不能少。

### 这一步必须调用已装的 UI skill（不要靠手感）

| Skill | 什么时候调 | 拿它来干什么 |
| --- | --- | --- |
| `ui-ux-pro-max` | **每次都调**，第三步一开始 | 移动端页面结构、信息层次、间距体系、交互态（hover/press/disabled/loading）、空态与错误态的成熟范式、配色与字体搭配、无障碍与对比度检查。查询用 `python3 scripts/search.py "<需求>" --stack {{STACK}}`；规则全文在 `references/quick-reference.md`，按需读，别整篇塞进上下文。 |
| `make-interfaces-feel-better` | 第三步末尾 + 第四步细节打磨 | 同心圆角（外圆角 = 内圆角 + padding）、光学对齐（带图标的按钮、播放三角）、阴影管景深/描边管结构、点击热区、数字用 tabular-nums、文字换行、进出场动画、**图标线重与文字字重匹配（`icons.md`）**。**这些正是最容易出"说不上哪里怪"的地方。** |
| `frontend-design` | **页面优化和求创新的时候调** —— 尤其是**可对外分享的页面**（分享页、邀请页、成就/报告页、落地页、新 App / 新品牌） | 版式个性、字体配对、hero 结构、动效编排、如何不显得像模板。 |

### 关于创新：要敢在原有设计语言上突破，但由用户决策

不要因为"现有代码是这样"就只做安全的复刻。**该创新的时候要敢提**，尤其是分享页这类会被用户发到社交平台、代表品牌门面的页面 —— 这类页面值得比 App 内页更强的视觉表达。

做法是**提案制，不是自作主张**：

- 在整合稿里把创新点做出来给用户看，或者给**两个方向对比**（保守版 vs 突破版），说清楚每个方向的取舍。
- 明确标出"这里我在现有设计语言上做了什么突破、为什么"，放在手机框外的说明里（框内仍然零解释）。
- **决策权在用户。** 提供参考和建议，让用户来定采用哪个、采用到什么程度。
- 用户拍板前，不要把突破性改动当成既定事实往后续页面上铺开。

### 冲突时的优先级

给**已有 App 加页面**时，顺序是：

1. **真实代码里的字体 / 配色 / 组件 / 文案**（第二步查到的）—— 默认基准。
2. 本 skill 里的硬规则（抽屉是抽屉、按钮吸底、页内零解释）—— 不可协商。
3. `ui-ux-pro-max` / `make-interfaces-feel-better` 的通用最佳实践。
4. `frontend-design` 的创新提案 —— 可以**挑战第 1 条**，但必须以提案形式交用户决策，不能直接替换掉既有语言。

如果某个 skill 的建议和真实代码实现冲突（比如建议换主色、换字体、换组件形态），**不要自己改掉**，按第四步的规则汇报给用户并记进 `{{DECISION_LOG}}`，由用户定。

## 第四步：核对，并和用户最后确定

- 对照**实际代码库**核实字体 / 配色 / 组件 / 文案，确保设计稿和真实实现对得上，不是凭空画的。
- **视觉问题必须真的看图核实，不能只读 HTML 源码猜。** 用 `{{SHOTS_SKILL}}` skill 逐屏出 PNG，然后用 Read 工具一张张看。按钮被拉伸、文字溢出、图标画错这类真实渲染 bug 只有看图才发现。
- **需求文档和代码矛盾的地方不许自己拍板选一个。** 如实汇报给用户，记录到 `{{DECISION_LOG}}`，由用户来定。（真实例子：文档写的支付渠道与代码实际接入的不一致；客服弹窗的结构文档与实现各说各话。）
- **每一批做完之后，主动再对照需求文档全文核一遍**，确认没有违反文档里"明确不展示 / 不出现"这类硬性规定。（真实例子：某资质页把文档明令禁止展示的证件号码和评价原文画了上去。）

## 第五步：拆成一个页面一个 HTML 文件

**只有用户明确确认整合版最终定稿之后才做这一步。**

- 每个页面 / 每个状态各自一个独立 HTML 文件，放 `{{MOCKUP_DIR}}`。
- 不能用同页面内切 Tab 假装是多个状态 —— **一个状态 = 一个页面**。

---

## 交付形式（硬约束）

- **阶段 1：只产出一份整合的 HTML**，所有页面/状态放在一起看整体流程，交给用户后**停下**。
- **审阅循环：** 用户在整合版上提意见，就一直改**这同一个文件**，不管改到多"终版"都不拆。
- **阶段 2：** 用户明确确认定稿后，才拆成一页一个的独立 HTML 给研发落地。
- 原因：先给用户一个便宜、好改的单一产物迭代，避免过早拆分导致每轮改动要在 N 个文件里重复。
- **审阅循环中哪怕某一轮看起来已经"终版"了，也不要提前拆** —— 只认用户明确的定稿确认。
- 这里说的"一个页面"= 一屏 / 一个状态，不是一个可切 Tab 的容器。

## 页面内零解释（硬约束）

输出的页面就是 App 最终呈现的样子，**不要在手机框里加任何批注**。

- 不加 "NEW / 新增" 等标签、功能序号。
- 不加需求编号 pill、图例、对照说明、常驻提示。
- 所有批注、状态之间的关系说明，都以文字形式放在**页面外**：手机框外的 deck 装饰（上方 `frame-tag` 标题、下方 `frame-cap` 说明、checklist 表格、`doc-header`），或写进注释 / 需求文档。
- 页内不做状态切换控件。**一个状态 = 一个独立手机框**，页内切 Tab 会让研发误判到底要做几屏、甚至以为切 Tab 本身是要实现的功能。
- 如果某一屏的目的就是**对比几种状态**，拆成几个独立手机框，把对比说明写进框外的 caption —— 不要把变体堆在同一个手机框里、中间加标签分隔。
- 具体禁止项（都是真出现过的）：需求编号 pill、说明性浮层、图标总表 / 图例、"情况一 / 情况二 / 情况三"这类分节标题、以及**真实 App 里点击才弹出、却被画成常驻**的提示气泡。
- 想标注"这块是新增的"，只能写在手机框下方的 `frame-cap` 或 checklist 的 tag 里。

## 组件样式硬规则

- **底部抽屉要画成真的抽屉**：贴屏幕底部、顶部圆角、后面有半透明遮罩、上层页面内容仍隐约可见。**不能铺满全屏** —— 铺满会让研发误建成一个整页而不是 sheet。确认弹窗、操作面板、筛选/编辑抽屉都适用。
- **底部主按钮要吸底**：整宽主按钮（或 1–2 个堆叠的整宽按钮）用 `position:sticky; bottom:0` 钉在手机框底部，背景色跟页面一致以免看起来透明。不能随内容长度浮动 —— 位置取决于内容高度会让研发觉得稿子没做完。（翻过车的真实场景：充值档位选择页的主 CTA、退款结果页的两个操作按钮，都曾跟着内容浮在半空。）
- 真实页面用 `{{SHELL_CLASS}}` 约定里的真实页面容器；规格图 / 对照图用规格容器（虚线卡 + ◇ 标记），只有后者允许出现说明性标注。

## 视觉一致性

页面"不精致"（字号、行距、间距不统一）的根因**在实现层，不是缺设计规范**：设计稿本身没问题，但用 AI 写代码落地时每个页面重新猜数值（`fontSize: 15`、`padding: 18`），累积成漂移；漂移之后又没人发现。

所以讨论视觉精度问题时，往**工程治理**方向走，别往"招个设计师建规范"走（设计师调好一版，下一版 AI 重写代码照样飘）：design token 唯一来源、禁止硬编码数值、lint 拦截、写进代码仓的 `CLAUDE.md`、screenshot diff 视觉回归。

给用户的验收方法必须是**「对比」而不是「评判」**：把"这个字号是不是大了"转译成"全项目一共用了几种字号值"。判断一致性不需要审美，判断好看才需要。

## 每次交付前的自检清单

1. 项目配置读了吗？用到的 `{{变量}}` 是否都有真实值（不是 `未配置`）？
2. 页面/状态清单是否齐全（空态、成功、失败、重试、未选中）？
3. 每个涉及原有实现的页面，原有信息是否一个不漏？
4. 第三步是否真的调了 `ui-ux-pro-max` 和 `make-interfaces-feel-better`，而不是凭手感调间距？
5. 有没有该提创新提案却没提？（分享页/对外页尤其要问自己这句）提了的话，是否明确交给用户决策而不是自己定了？
6. 是否跑过 `{{SHOTS_SKILL}}` 并**逐张看过图**？
7. 手机框里是否混进了解释性内容 / NEW 标签 / 需求编号？
8. 抽屉是抽屉吗？底部按钮吸底了吗？
9. 字体/配色/组件/文案是否对得上真实代码？（创新提案除外，但提案必须已标注并待用户决策）
10. 需求文档里"明确不展示"的东西是否真的没出现？
11. 文档与代码的矛盾是否已写进 `{{DECISION_LOG}}` 并汇报给用户？
12. 还在整合版阶段吗？没拿到明确定稿确认就**不要拆文件**。
