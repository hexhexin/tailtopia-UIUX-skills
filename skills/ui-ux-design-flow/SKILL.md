# UI/UX 设计标准工作流

**这是用户明确确认过的工作方式，不是建议。开始画任何一屏之前先读完，然后按顺序执行。**

一句话：**完整度 → 代码对齐 → 美观 → 细节优化**。每一步做完都要如实核对、不自己瞎拍板、发现问题直接改并留痕。

---

## 第一步：从 PRD 推导完整页面清单

目标是**页面结构不缺**，不是先画得好看。

- 通读 PRD，把这个聚类涉及的**所有页面/所有状态**全部列出来，做成 checklist。
- 必须包含（最容易漏的就是这些）：
  - **空态**（数据为空白的状态）
  - **重试 / 加载 / 异常态**
  - 重要页面的**操作成功页**、**操作失败页**
  - **未选中 / 默认未填 / 禁用**等样式
- 列完之后**主动核对一遍有没有漏页**，确认逻辑上不存在缺失的中间页（比如有确认页没有结果页、有列表没有空列表）。
- 这一步的产出是清单 + 页面跳转关系，先给用户过一遍再往下走。

## 第二步：结合代码补齐清单中的页面（含原有实现）

新增内容必须长在**真实的现有页面**上，不是凭空画一个新页面。

- 去 `petgo-platform` 仓库（<https://github.com/DaiHanWei/petgo-platform.git>）查每个涉及页面的**现有实现**：这个页面原本有哪些信息模块、什么顺序、什么组件。
  - 分支约定见记忆 `reference_tailtopia_petgo_branches`（`main` = 线上，`stag` = 在做的新版本）。
- 把原页面的信息**一个都不漏地**先摆回去，再决定 PRD 新增的模块插在哪、怎么排。
- 然后在"修正后的页面"基础上优化新增内容加入后的样式/排版/布局。
- **画每一屏之前先对着代码验证逻辑**，别把 PRD 字面直译成像素 —— 见记忆 `feedback_tailtopia_ui_verify_logic_first`。

## 第三步：页面样式优化

完整度过关之后，才动配色、间距、视觉层次。

- 这一步要**有创意**、保证视觉美观性。
- 同时**不能因为好看而丢信息** —— 该页面应该展示的信息一个都不能少。

### 这一步必须调用已装的 UI skill（不要靠手感）

| Skill | 什么时候调 | 拿它来干什么 |
| --- | --- | --- |
| `ui-ux-pro-max` | **每次都调**，第三步一开始 | 移动端页面结构、信息层次、间距体系、交互态（hover/press/disabled/loading）、空态与错误态的成熟范式、配色与字体搭配、无障碍与对比度检查。它有 mobile app / 161 产品类型的现成规则，别自己重新发明。 |
| `make-interfaces-feel-better` | 第三步末尾 + 第四步细节打磨 | 同心圆角（外圆角 = 内圆角 + padding）、光学对齐（带图标的按钮、播放三角）、阴影优于描边、点击热区、数字用 tabular-nums、文字换行、进出场动画。**这些正是最容易出"说不上哪里怪"的地方。** |
| `frontend-design` | **页面优化和求创新的时候调** —— 尤其是**可对外分享的页面**（分享页、邀请页、成就/报告页、落地页、新 App / 新品牌） | 版式个性、字体配对、hero 结构、动效编排、如何不显得像模板。 |

### 关于创新：要敢在原有设计语言上突破，但由用户决策

不要因为"现有代码是这样"就只做安全的复刻。**该创新的时候要敢提**，尤其是分享页这类会被用户发到社交平台、代表品牌门面的页面 —— 这类页面值得比 App 内页更强的视觉表达。

做法是**提案制，不是自作主张**：

- 在整合稿里把创新点做出来给用户看，或者给**两个方向对比**（保守版 vs 突破版），说清楚每个方向的取舍。
- 明确标出"这里我在现有设计语言上做了什么突破、为什么"，放在手机框外的说明里（框内仍然零解释）。
- **决策权在用户。** 提供参考和建议，让用户来定采用哪个、采用到什么程度。
- 用户拍板前，不要把突破性改动当成既定事实往后续页面上铺开。

### 冲突时的优先级

给**已有 App 加页面**时，顺序是：

1. **真实代码里的字体 / 配色 / 组件 / 文案**（第二步查到的）—— 默认基准。
2. 本 skill 里的硬规则（抽屉是抽屉、按钮吸底、页内零解释）—— 不可协商。
3. `ui-ux-pro-max` / `make-interfaces-feel-better` 的通用最佳实践。
4. `frontend-design` 的创新提案 —— 可以**挑战第 1 条**，但必须以提案形式交用户决策，不能直接替换掉既有语言。

如果某个 skill 的建议和真实代码实现冲突（比如建议换主色、换字体、换组件形态），**不要自己改掉**，按第四步的规则汇报给用户并记进 `.decision-log.md`，由用户定。

## 第四步：核对，并和用户最后确定

- 对照**实际代码库**核实字体 / 配色 / 组件 / 文案，确保设计稿和真实实现对得上，不是凭空画的。
- **视觉问题必须真的看图核实，不能只读 HTML 源码猜。** 用 `tailtopia-ui-shots` skill 逐屏出 PNG，然后用 Read 工具一张张看。按钮被拉伸、文字溢出、图标画错这类真实渲染 bug 只有看图才发现。
- **PRD 和代码矛盾的地方不许自己拍板选一个。** 如实汇报给用户，记录到 `.decision-log.md`，由用户来定。（历史例子：支付渠道 DANA、客服弹窗结构。）
- **每一批做完之后，主动再对照 PRD 全文核一遍**，确认没有违反 PRD 里"明确不展示 / 不出现"这类硬性规定。（历史例子：兽医资质页展示了明令禁止的证件号码和评价原文。）

## 第五步：拆成一个页面一个 HTML 文件

**只有用户明确确认整合版最终定稿之后才做这一步。**

- 每个页面 / 每个状态各自一个独立 HTML 文件。
- 不能用同页面内切 Tab 假装是多个状态 —— **一个状态 = 一个页面**。

---

## 交付形式（硬约束）

- **阶段 1：只产出一份整合的 HTML**，所有页面/状态放在一起看整体流程，交给用户后**停下**。
- **审阅循环：** 用户在整合版上提意见，就一直改**这同一个文件**，不管改到多"终版"都不拆。
- **阶段 2：** 用户明确确认定稿后，才拆成一页一个的独立 HTML 给研发落地。
- 原因：先给用户一个便宜、好改的单一产物迭代，避免过早拆分导致每轮改动要在 N 个文件里重复。
- 详见记忆 `feedback_tailtopia_ui_deliverable_format`。

## 页面内零解释（硬约束）

输出的页面就是 App 最终呈现的样子，**不要在手机框里加任何批注**。

- 不加 "NEW / BARU"、功能序号等标签。
- 不加 FR 编号 pill、图例、对照说明、常驻提示。
- 所有批注、状态之间的关系说明，都以文字形式放在**页面外**：手机框外的 deck 装饰（上方 `frame-tag` 标题、下方 `frame-cap` 说明、checklist 表格、`doc-header`），或写进注释 / PRD。
- 页内不做状态切换控件。
- 详见记忆 `feedback_tailtopia_ui_no_fr_labels_in_mockup`、`feedback_tailtopia_ui_no_new_tags_no_tabs`。

## 组件样式硬规则

- **底部抽屉要画成真的抽屉**：贴屏幕底部、顶部圆角、后面有半透明遮罩、上层页面内容仍隐约可见。**不能铺满全屏**。见记忆 `feedback_tailtopia_ui_bottom_sheet_style`。
- **底部主按钮要吸底**，不能随内容长度浮动。见记忆 `feedback_tailtopia_ui_sticky_bottom_cta`。
- 真实页面用 `.phone-shell`；规格图 / 对照图用 `.spec-shell`（虚线卡 + ◇ 标记），只有后者允许出现中文标注。

## 视觉一致性

视觉漂移的根因在实现层（AI 编码漂移 + 无人验收），不是缺规范。用**数值一致性检查**代替人眼扫一遍。见记忆 `feedback_tailtopia_visual_drift_is_implementation_layer`。

## 每次交付前的自检清单

1. 页面/状态清单是否齐全（空态、成功、失败、重试、未选中）？
2. 每个涉及原有实现的页面，原有信息是否一个不漏？
3. 第三步是否真的调了 `ui-ux-pro-max` 和 `make-interfaces-feel-better`，而不是凭手感调间距？
4. 有没有该提创新提案却没提？（分享页/对外页尤其要问自己这句）提了的话，是否明确交给用户决策而不是自己定了？
5. 是否跑过 `tailtopia-ui-shots` 并**逐张看过图**？
6. 手机框里是否混进了解释性内容 / NEW 标签 / FR 编号？
7. 抽屉是抽屉吗？底部按钮吸底了吗？
8. 字体/配色/组件/文案是否对得上真实代码？（创新提案除外，但提案必须已标注并待用户决策）
9. PRD 里"明确不展示"的东西是否真的没出现？
10. PRD 与代码的矛盾是否已写进 `.decision-log.md` 并汇报给用户？
11. 还在整合版阶段吗？没拿到明确定稿确认就**不要拆文件**。
